# SMM — запись сессии для будущих скриптов

Один раз пройти сценарий руками в браузере и получить всё, из чего потом пишется скрипт
или автоматизация: шаги с локаторами, последствия каждого шага, сетевой контракт
приложения, способ авторизации и список того, что осталось выяснить у оператора.

Инструмент не привязан к конкретному сайту: имя test-id атрибута, семантика компонентов и
правила захвата тел определяются в рантайме (см. `v7.2` в шапке скрипта).

## Запуск

**Расширение — основной способ.** `chrome://extensions` → Developer mode → Load unpacked →
папка репозитория. На панели браузера появится кнопка SMM, в ней только три вещи:

* **Старт** — запись идёт на всех сайтах и во всех вкладках сразу, на значке горит `REC`;
* **комментарий** — что вы сейчас делаете и зачем (Ctrl+Enter). Он ложится в таймлайн с
  текущей страницей и скриншотом: для ИИ это главный источник смысла;
* **Стоп и скачать архив** — открывается вкладка, и один файл `smm-<id>.zip` сам уходит в
  загрузки. Запись хранится в расширении до следующего «Старт», так что архив можно скачать ещё раз.

Сессией владеет расширение (`ext/background.js`, IndexedDB расширения), а не страница.
Поэтому её не обрывают переход на другой сайт или поддомен (SSO, редиректы), перезагрузки,
новые вкладки, закрытие вкладки и перезапуск service worker. Раньше запись лежала в
`localStorage` страницы: другой origin означал новую сессию, а две вкладки одного сайта
затирали друг другу бэкап.

Что пишется:

* в каждом документе — всё, что умеет `action-logger-v7.js`: шаги с локаторами, ввод,
  последствия, тела fetch/XHR, WebSocket/SSE, эндпоинты, авторизация;
* браузером — вкладки, переходы с типом (ссылка, ввод адреса, редирект, назад), **все**
  запросы, включая документы, формы и редиректы, загрузки файлов;
* скриншот видимой вкладки на каждом шаге, загрузке, переключении вкладки и комментарии;
* HTML страницы и её «поверхность»: ссылки, формы с полями, кнопки, заголовки. Снимается
  при загрузке, смене адреса и после шагов.

**Консоль DevTools** — на один раз, без установки, с прежней панелью:

```js
// вставить содержимое action-logger-v7.js в консоль на нужной странице
__logger.setMacroName('add-js-asset');   // иначе имя выведется из URL
```

Такая запись живёт, пока жива страница, и знает только один сайт.

## Архив

| Файл | Что внутри |
| --- | --- |
| `README.md` | инструкция для ИИ: что где лежит и в каком порядке читать |
| `session.json` | весь таймлайн по времени (все сайты и вкладки), страницы, комментарии, счётчики |
| `pages/NNN-…/bundle.json` | полный AI bundle логгера по одному документу (см. ниже) |
| `pages/NNN-…/dom-*.html`, `*.surface.json` | HTML и «поверхность» страницы |
| `screenshots/*.jpg` | скриншоты, время и причина в имени |
| `sitemap.json` | по каждому сайту: где был человек и какие ссылки он видел, но не открыл, плюс все формы — с этого начинается обход для скриптов-исследователей |
| `endpoints.json` | инвентарь API со всех страниц |
| `network/requests.json` | все запросы браузера (метаданные) |
| `network/session.har` | HAR 1.2 по fetch/XHR всех страниц, с телами |

## Команды консольного режима

| Команда | Зачем |
| --- | --- |
| `__logger.setMacroName('...')` | различать записи по имени файла, а не по id сессии |
| `__logger.beginTask({ page: '/ru/about' })` / `endTask({ status: 'ok' })` | резать плоский таймлайн на задачи — обычно «одна страница» |
| `__logger.mark('начинаю сохранение')` | метка в таймлайне (Ctrl+Shift+M) |
| `__logger.note('тут всегда лагает')` | человеческая заметка к текущему шагу |
| `__logger.expect({ type: 'text', value: 'Сохранено' })` | ассерт, который знает оператор, а не логгер |
| `__logger.registerProbe('state', () => app.store.getState())` | предметный снапшот приложения до/после шага |
| `__logger.stop()` | финализация + экспорт (Ctrl+Shift+S) |

Пауза, режим (`macro`/`debug`), статистика и все экспорты есть кнопками в панели в правом
нижнем углу.

## Что получается на выходе

| Экспорт | Что внутри | Когда нужен |
| --- | --- | --- |
| `__logger.export()` | полный AI bundle: таймлайн, снапшоты, сеть, эндпоинты, авторизация, стримы, черновик ТЗ и Playwright | по умолчанию — это и есть «всё» |
| `__logger.exportPlan()` | компактный рецепт без снапшотов и тел сети | когда bundle слишком велик для чата |
| `__logger.exportApi()` | только инвентарь эндпоинтов + профиль авторизации | когда пишется автоматизация на API, а не на кликах |
| `__logger.exportHar()` | сетевая часть в HAR 1.2 | DevTools, Postman, Insomnia, кодогенераторы |
| `__logger.exportPlaywright()` | отдельный `.spec.js` | когда нужен сразу тест, а не описание |
| `__logger.exportMacro()` | сырой список действий | отладка самого логгера |

Если скачивание заблокировано CSP — `__logger.copyLast()` положит последний экспорт в
буфер обмена.

## Ключевые поля, которые стоит понимать

**`endpoints[]` — API, который сценарий на самом деле потрогал.** Вызовы сгруппированы по
`METHOD + шаблон пути`: `/api/pages/1428/assets` и `/api/pages/1429/assets` — это один
эндпоинт `POST /api/pages/{int}/assets`, а не два. У каждого: статусы, шаги-инициаторы
(`triggeredBy`), имена нужных заголовков, форма запроса и ответа, `write: true` если он
меняет состояние, `background: true` если его не вызвал ни один шаг.

Форма тела — объединение всех записанных вызовов, а не последний из них:

```json
{ "src": "string", "async": { "__optional": "boolean" }, "id": { "__oneOf": ["number", "null"] } }
```

`__optional` — ключа не было хотя бы в одном вызове. `__oneOf` — на этом месте встречались
разные типы. Писать клиент надо по форме, а не по одному записанному значению.

**`authProfile` — как входить.** Механизм (`bearer_header` / `browser_cookies` /
`unknown`), имена cookie и форма их значений, ключи storage, похожие на токен, запросы,
похожие на логин, и готовая рекомендация. Пустой список cookie **не** значит «cookie не
используются»: `HttpOnly`-cookie из JS не видны вообще, и в профиле об этом сказано прямо.

**`streams[]` — WebSocket и SSE.** Кадры с привязкой к шагу, который их вызвал. Если шаг
поменял состояние, но HTTP-запроса в записи нет — смотреть надо здесь, прежде чем решать,
что запись неполная.

**`__UNPARSED__` ≠ `null`.** `responseJson: "__UNPARSED__"` означает «тело было, но это не
JSON» (текст лежит в `responsePreview`). `responseJson: null` означает, что сервер ответил
литеральным `null`. `responseBodyCaptured: false` — тело не читали вовсе. Три разных факта,
которые нельзя путать при написании клиента.

**`openQuestions[]` — чек-лист к оператору.** Слабые локаторы, возможные `retry`,
разрушительные шаги без видимого эффекта, неизвестный источник токена или CSRF, эндпоинт,
который ни разу не ответил успешно. Это то, что надо выяснить **до** написания скрипта, а не
на первом запуске.

## Как отдать запись ассистенту

Отдайте архив `smm-*.zip` целиком: его `README.md` объясняет ИИ, что где лежит, а каждый
`bundle.json` несёт `aiInstructions` с правилами чтения и `openQuestions` с тем, что надо
спросить. Полезно приложить к нему задачу:

> Вот архив записи моей работы (SMM). Сначала прочитай его README.md.
> 1. Сначала выдай `openQuestions[]` одним списком — я отвечу, прежде чем ты начнёшь писать код.
> 2. Скажи, можно ли автоматизировать это на уровне API (`brief.apiFirstFeasible`,
>    `endpoints[]` с `write: true`) или придётся остаться на UI-уровне, и почему.
> 3. Что нужно для авторизации — по `authProfile`, не угадывая.
> 4. Только после этого — скрипт. Локаторы с `locatorConfidence.level === 'low'` не
>    использовать как есть, `destructive: true` шаги — под подтверждение, значения
>    `[REDACTED]` — параметрами, а не константами.

## Секреты

Записывается, **как** приложение авторизуется, и никогда — **чем**:

* значения заголовков `authorization`, `cookie`, `set-cookie`, `x-csrf-token`, `x-api-key`
  и подобных заменяются на `[REDACTED]`, но **имена сохраняются** — без них запрос
  невозможно воспроизвести, а значение всё равно придётся брать заново;
* поля тела, чьи имена похожи на секрет (`password`, `token`, `secret`, `api_key`, ...),
  редактируются на любой глубине;
* значения `input[type=password]` и полей с «секретными» именами не записываются;
* значения cookie и токенов из storage не записываются — только имя, форма (`jwt`, `hex`,
  `base64ish`) и длина;
* инлайновый `Bearer <token>` вычищается и из не-JSON тел.

Расширение, пока идёт запись, видит **все** сайты и вкладки: скриншоты и снимки HTML
показывают страницу как есть, со всем, что на ней написано. Перед личными делами (почта,
банк) запись нужно остановить. Между записями расширение ничего не пишет и не внедряет.

Тем не менее экспорт — это подробный след работы с внутренним приложением: URL, структуры
ответов, имена сущностей. Обращаться с ним нужно как с внутренним документом.

## Разработка

```bash
npm ci
npm run lint              # node --check: синтаксис нельзя узнавать посреди записи
npm test                  # чистые функции: редакция, инвентарь, HAR, профиль авторизации
npm run test:integration  # живая запись в Chromium (нужен npx playwright install chromium)
npm run check             # всё вместе
```

Блок между `// --- PURE-HELPERS-BEGIN ---` и `// --- PURE-HELPERS-END ---` в
`action-logger-v7.js` не имеет права обращаться к `config`, `document` или журналам: он
вырезается из исходника и исполняется в node (`test/helpers/load-pure.mjs`), и тест на это
специально смотрит. Новую логику разбора/редакции/сведения лучше писать там — тогда она
проверяема без браузера.

Дисциплина работы с сетевыми данными (parse → redact → bound; `UNPARSED` вместо `null`;
имена секретных заголовков сохраняются, значения — нет) взята из соседнего проекта
Migrator, `python/src/migrator/network/recorder.py`, где эти правила появились после
реальных потерь данных.
